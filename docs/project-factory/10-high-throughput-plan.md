# PortBridge 2.5G 高速通信架构与实机验收方案

## 1. 已知约束及证据边界

用户补充：需要 TCP 和 UDP，网络接口约为 2.5G，遇到过报文丢失。因此高速通信是首版的架构约束，不能等界面完成后再补性能设计。

原先 Qt Socket 程序的抓包、源码和实际包长/包率仍未提供，不能确认用户遇到的丢失发生在解析、系统接收队列、网卡或发送端。本项目现已实现 Windows/IPv4、Qt Widgets + Asio 核心，并完成真实 localhost 功能与基线测试；这不定位原程序的丢失原因，也不证明真实 2.5G 性能。Qt Socket 不自动等同于低性能；Asio 或原生 Socket 也不自动保证零丢失。

## 2. 量级与容量

2.5 Gb/s / 8 = 312.5 MB/s，为网口标称速率的字节换算，不是应用有效吞吐保证。以下为无 VLAN、IPv4、无选项、常见以太网开销下的粗略单方向估算：

| 场景 | 约计量级 | 意义 |
| --- | --- | --- |
| MTU 1500、UDP payload 1472 字节 | 满链路约 20 万报/秒、约 300 MB/s 有效负载 | 已需要控制逐包分配、复制、事件投递开销 |
| 最小以太网帧 | 计入前导码与帧间间隔约 370 万帧/秒 | 小报文的 PPS 压力远高于大报文，不能仅验收 MB/s |
| 原始负载约 300 MB/s | 约 1.08 TB/小时 | 满速连续保存需要验证持续磁盘速度、空间和保留策略 |
| HEX 连续编码 | 原始数据约 2 倍，空格分隔时约 3 倍 | 不能将满速原始数据逐字节转 HEX 并实时显示/落盘 |
| 接收端停顿 100 ms | 在 312.5 MB/s 估算下累计约 31.25 MB | 缓冲只能覆盖有限停顿，不能解决长期消费速度不足 |

网口可能全双工；若需同时满速收发，内存/CPU/记录量需按双方向重新计算。实际报文长度、TCP ACK、网卡 offload 和协议开销会影响结果。上述数字是容量估算，未实测。

## 3. 区分丢失类型

- **TCP 字节流**：正常连接上的网络包丢失由 TCP 重传处理。读取变慢通常造成接收窗口收缩和发送背压，并非 Socket 自动丢掉成功接收的字节。业务帧缺失需检查发送端、应用缓冲溢出、分帧逻辑、部分写入、连接复位/中断及记录完整性。对端可能因实时性超时或自身队列满而丢业务数据，也要纳入定位。
- **UDP 数据报**：没有可靠交付或对端背压；网卡、内核队列、接收截断和应用队列均可能造成真实丢失。换库能改善接收效率，但不能恢复上游已丢的数据。
- **显示抽样**：高速模式有意不显示全部数据；这不是接收丢包。必须与原始接收、记录丢弃分别计数。
- **业务帧缺失**：需要已知协议序号或独立发送清单才能判断。应用自行生成的日志序号只能发现本地记录问题，不能判断到达应用前丢失的数据。

## 4. 后端候选与建议

| 方案 | 优点 | 代价/限制 | 定位 |
| --- | --- | --- | --- |
| Qt Socket + 独立 I/O 线程 | 依赖少，功能成熟；与其他方案使用同一测试条件 | 需要消除 UI/逐包信号开销；UDP 批处理控制较少 | 对照基线，不作为未经验证的高速默认后端 |
| standalone Asio | 跨平台异步 C++ 核心；可独立于 Qt；Windows 通常使用 overlapped I/O/IOCP，Linux 通常使用 epoll | 仍需管理缓冲、生命周期、队列和完成回调；普通异步 UDP 接收不自动变成多数据报批处理 | 已实现并通过功能测试；物理负载验证仍待执行 |
| Windows 原生 Winsock/IOCP | 可控制预投递接收、复用缓冲和完成队列，适合专项优化 | 开发与维护成本更高；并发完成时不能破坏 TCP 流顺序；平台绑定 | Asio 未达到目标且瓶颈位于接收路径时评估 |
| Windows RIO | 注册缓冲与请求/完成队列可用于减少部分开销 | 需要运行时获取扩展、验证目标系统/provider 支持并提供降级；不保证在目标负载一定更快 | 高 PPS UDP 专项候选 |
| Linux epoll + recvmmsg | 可用一次系统调用读取多个 UDP 数据报 | 原生适配与调度、公平性、缓冲管理仍需实现 | Linux 高 PPS UDP 专项候选 |

已采用 Qt Widgets + 可替换的 C++ 网络核心，实现 Asio 独立收发工具与完整 TCP/UDP 产品功能；若两机目标负载不达标且瓶颈位于接收路径，再根据样机对照结果评估原生 Winsock/IOCP。不给多个后端同时开发完整产品功能，先验证再收敛。

不建议仅因 2.5G 口就引入 DPDK、内核旁路或全面改写串口；是否需要这些技术须由负载与瓶颈决定。

## 5. 数据管线

推荐流向：网络 I/O → 复用的原始数据块 → 有界处理/记录队列 → 二进制记录；UI 从旁路获得有限样本和统计快照。

关键要求：

1. 网络接收与 Qt UI 线程分离；收包过程不等待文本显示、同步磁盘写入或昂贵解析。
2. 复用缓冲池，减少逐包 heap 分配和重复复制。缓冲生命周期须明确，异步 I/O 完成及所有消费者释放前不得复用；不宣称无条件零拷贝。
3. 接收、解析、日志和 UI 各自有队列预算，记录队列高水位和饱和次数。可先使用简单有界队列，确有锁竞争证据再引入专用无锁实现。
4. 不对每个 UDP 数据报或 TCP 读取块向 UI 发 queued signal。UI 定时获取快照并展示有限批次；建议 10–30 Hz 起步，以响应测试调整。
5. CPU 密集解析放独立处理阶段；TCP 按连接保存顺序，UDP 的来源和报文边界不能在批量缓存中丢失。
6. TCP 记录队列达到上限时暂停提交新的接收/消费并使用 TCP 背压，或主动终止本次记录并报告；不能静默丢字节。对端持续不受控时仍可能超时/断开，需记录。
7. UDP 队列饱和时继续尽快处理接收并执行明确的丢弃策略，统计应用丢弃；本地暂停接收不能让发送端自动降速。需无损交付时增加协议限速/重传或改用可靠传输。
8. 写入结果、关闭、取消和工作线程结束顺序明确；退出时有限等待，并报告未写入的数据量。

## 6. 首版需要增加的能力

- **普通调试模式**：文本/HEX 详细显示、命令发送、可读日志；仍使用独立通信管线。
- **高速接收模式**：优先展示速率、累计字节/包、错误、队列水位和数据样本；抽样显示数量可调，标明未展示数量。
- **二进制采集**：后台大块顺序写原始数据与索引，保留 TCP 连接身份、UDP 报文长度/来源/时间。离线再导出文本/HEX/JSON。
- **采集限制**：配置时长、大小和轮转策略，展示持续写入速度和剩余空间；模式切换不能自动提高原始日志要求而不提示容量变化。
- **丢失诊断**：区分发送器计数、应用收到、解析有效、应用队列丢弃、记录失败、显示抽样；内核/网卡统计只在平台可观测范围内提供，未知不能标为零。
- **协议序号分析**：压测数据内置 64 位序号和 payload 校验。真实协议有序号时再启用相应分析；UDP 乱序先进入有限重排/观察窗口，再判定缺失，单独统计重复和迟到。
- **缓冲设置**：允许配置系统 socket 接收/发送缓冲、应用缓存；读取实际生效值。QUdpSocket 的 setReadBufferSize 不控制其内核接收队列，不能将两者混用。

## 7. 压测方案与后端选型门槛

先做无界面的接收与发送样机，再加入日志和 UI。使用 Release 构建与一致的测试数据、接收预算、协议和测试时长。

### 环境

使用两台真实机器、真实 2.5G 网卡及符合链路要求的交换机/直连环境。记录操作系统、CPU、内存、驱动、MTU、网卡 offload 设置、磁盘持续写入性能及电源模式。回环仅用于功能测试，不代表网卡链路性能。

### 负载矩阵

- TCP：不同写入块大小；接收端主动切分，保证协议解码与块边界无关。
- UDP：64、256、1024、1472 字节 payload，先记录实际设备典型长度，再补其他长度；若使用 jumbo frame 另列条件。
- 分别按约 10%、50%、80%、95% 可用链路负载测试持续收发与突发；必须同时记录 PPS 和有效负载 MB/s，不能从理论字节换算直接决定小包发送率。
- 依次测试仅接收、接收+二进制记录、接收+UI 抽样、全部开启；按实际需要追加双向收发及多客户端。
- 注入 UI 停顿、磁盘变慢、网络断开和队列饱和，确认这些问题不会静默表现为“正常”。

### 指标

记录有效吞吐、PPS、CPU、内存、接收/记录队列高水位、磁盘写速、发送端实际完成数、接收有效数、序号缺口/乱序/重复、应用丢弃、接收截断和记录失败。延迟百分位若跨机器测量需定义时钟同步，未同步时不宣称准确单向延迟。

网卡/内核指标通常按接口或系统统计，不一定能归因到单个 socket。外部抓包也可能丢包，且会改变测试负载；作为定位证据时同时报告抓包器丢弃计数，避免用一份不完整抓包直接判定应用丢包。

### 正式验收

具体持续吞吐、包率、包长、突发窗口和测试时长在取得实际设备数据后固定。目标链路为 2.5G，但当前不承诺任意包长/任意突发下满速 UDP 零丢包。

- TCP：完整连接且发送确认完成的测试数据，在接收/记录完成后字节数、顺序、协议序号及校验一致；背压导致吞吐不足应报告，不能静默丢弃。
- UDP：给出每个包长下可复现的最大无应用丢弃负载、端到端丢失率及突发能力；确认测试发送器能达到设定速率。业务若要求特定负载零丢失，须在受控环境以该条件验收。
- UI：在声明负载下操作仍有响应，抽样数有明确标识；原始接收不会依赖 UI 刷新进度。
- 记录：无记录队列溢出且磁盘能持续承载所声明负载；出现容量不足明确失败/降级，不继续宣称完整记录。

## 9. 本轮实施结果与后续实机步骤

已实现 standalone Asio 1.30.2 异步核心、分级缓冲复用（payload只弱引用池，已退休空闲缓存不随样本保留）、有界 TX/描述符、TCP 保留块背压、UDP 来源/空报文/明确丢弃、真实生效 socket 缓冲、Windows UDP 目标 ICMP 非终止错误、独立 serial/record/export 工作线程及50ms GUI批处理。记录格式、具体边界与审查证据见 08-acceptance-report.md、docs/reviews/。

已完成的 localhost 基线：UDP 1472字节、请求20,000帧/秒、2秒，40,000完成/接收；TCP 16,384字节、请求5,000帧/秒、2秒，10,000完成/接收。两者缺失/校验失败均0。完整机器可读结果在 docs/validation/localhost-{udp,tcp}.json，明确 UI/记录关闭、physical_2_5g_validated=false、kernel_or_nic_drops=null。这些是功能基线，未寻找最大吞吐，也没有 Qt Socket/原生后端实测比较。

下一轮使用实际设备包长/PPS及两台2.5G机器执行第7节矩阵，分别带上 UI/记录/双向条件，并记录达到的发送速率；不要把 requested rate 当成 achieved rate。以发送器实际完成数作为接收端 --expected，区分发送未达目标、网络缺失、应用/记录队列、显示裁剪。串口设备和持续磁盘写入另行实测。
